# Design doc: maintainable public Toolkit documentation pack

## Context

Публичный репозиторий `NickScherbakov/toolkit` не содержит исходный код Infostart Toolkit и фактически используется как точка входа для обратной связи, release-notes и вспомогательной документации. Это подтверждено `README.md`, историей коммитов и составом файлов в ветке `master`.

Из-за отсутствия продуктовых исходников невозможно подготовить честный PR с реализацией внутренних изменений Toolkit, модульными тестами продукта и полноценной CI-проверкой закрытого кода. Поэтому PoC в этом PR ограничен тем, что реально находится в репозитории: публичным описанием инструментария, шаблонами triage и автоматизацией качества документации.

## Goals

1. Сделать публичный каталог инструментов поддерживаемым и проверяемым.
2. Зафиксировать ограничения публичного репозитория и критический блокер по отсутствию исходников.
3. Добавить CI и тесты для тех артефактов, которыми этот репозиторий действительно владеет.
4. Подготовить migration pack для перехода от разрозненных markdown/docx/pdf описаний к структурированному каталогу.

## Non-goals

1. Реализация закрытых функций Infostart Toolkit.
2. Изменение организационных настроек GitHub Actions.
3. Публикация или реконструкция проприетарного исходного кода.

## Proposed architecture

### 1. Machine-readable catalog

Добавляется `data/toolkit_catalog.json` с тремя сущностями:

- `tools`: перечень инструментов из README в фиксированном порядке;
- `improvements`: приоритизированный backlog улучшений, сформированный по документам репозитория;
- `critical_blockers`: блокеры, из-за которых продуктовая реализация невозможна в публичном репозитории.

Этот файл становится опорным источником для автоматических проверок и дальнейшей эволюции документации.

### 2. Validation layer

`scripts/validate_catalog.py` выполняет проверки:

- README и каталог описывают один и тот же набор инструментов;
- slug и имена не дублируются;
- backlog содержит валидные приоритеты;
- блокеры явно размечены как `critical`.

Скрипт формирует `build/validation-report.md`, который можно прикреплять как artifact в CI.

### 3. Test layer

`tests/test_catalog.py` фиксирует основные инварианты каталога. Это дает минимальную регрессионную защиту при обновлении README, issue templates и migration pack.

### 4. CI layer

Workflow `.github/workflows/ci.yml` запускает:

1. `python -m compileall scripts tests`
2. `python scripts/validate_catalog.py --report build/validation-report.md`
3. `python -m unittest discover -s tests -v`

Артефакт `validation-report` хранится 30 дней.

## API and compatibility impact

Пользовательский API продукта не меняется, потому что публичный репозиторий не содержит самого продукта. Меняется только внутренний формат сопровождения документации:

- раньше список инструментов поддерживался вручную в нескольких местах;
- теперь вводится явный каталог как source of truth для публичной документации.

Обратная совместимость сохраняется: существующие markdown-файлы и ссылки остаются доступными.

## Dependencies

Новые runtime-зависимости не добавляются. PoC использует только стандартную библиотеку Python и официальные GitHub Actions:

- `actions/checkout@v4`
- `actions/setup-python@v5`
- `actions/upload-artifact@v4`

## Security considerations

1. Секреты в репозиторий не добавляются.
2. Workflow не требует организационных разрешений и не меняет org-level CI settings.
3. Публично фиксируется критический блокер: без приватных исходников и внутренних тестов нельзя обещать продуктовые исправления.

## Rollback plan

Если переход на каталог окажется неудобным:

1. удалить `data/`, `scripts/`, `tests/` и workflow;
2. вернуть сопровождение README и docs в ручной режим;
3. оставить design doc и backlog как аналитический артефакт.

Такой откат не затрагивает пользовательские данные и не меняет продуктовое поведение Toolkit.
